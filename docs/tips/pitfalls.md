# 落とし穴集(参加記から)

- Goの変更が反映されていなかった: systemctl restartだけではビルドされない。ビルドとデプロイを必ず同じスクリプトに入れる(scripts/deploy.shが担当)
- インデックスが3台のうち1台にしか入っていなかった: 構成変更後は全台の状態を確認する
- ソースの変更が巻き戻って作業が消えた: 各自のworktreeで作業し、pushしてから試す(docs/workflow.md)
- 複数人が同時に検証して、どの変更の効果か分からなくなった: リースで検証を直列化する
- 前回の環境が競合して構築に失敗した: 以前の練習環境のCloudFormationスタックなどは先に削除する
- 初期スコアは後から比較できるよう必ず記録する
- 設定ファイルが複数あり、効いていない方を編集していた: `nginx -T`で有効な設定を確認する
- ログの無効化でエラーが見えなくなった: 無効化前にエラーが出ていないことを確認する
- 提出前にスロークエリログ、デバッグ出力、計測用エンドポイントを外す
- 整合性チェックが落ちる最適化(強すぎるキャッシュ、画像の書き出し漏れ)は得点が0になる。passがfalseなら直前の変更を戻す
- nginx.confのhttp{}にすでにaccess_logがあるのに、conf.dへ別のaccess_logを足すと二重に出力される。nginx.confのログ設定を直接置き換える
- 古いAMIの練習環境では証明書の期限切れ、DNSが返すIPの不一致でベンチが通らない(ISUCON13の例はisucon13/README.mdの記録を参照)
- ベンチマーカーはログを標準出力と標準エラー出力に分けて出すことがある。結果の取得は両方を記録する
- ssh経由でリモートに渡す引数は、空白を含むと分割される。scripts/lib.shのssh_bashのようにクォートして渡す
- スロークエリログの初期化で`truncate`を使うと、存在しないファイルがroot所有で作られ、MySQLが書けずにログがOFFのままになる。`truncate -c`を使い、MySQLに作らせる
