# 進め方の指針

ISUCON13の練習環境で一通り回した結果から、効果があった進め方をまとめる。根拠は[improvement-loop.md](improvement-loop.md)の実施記録。

## 最初にやること(順番固定)
1. 初期スコアを3回計測し、ばらつきを把握する(ISUCON13では3357〜3553、約6%)。これより小さい差は改善とみなさない
2. 計測用の設定だけを入れて計測する。nginxのLTSVログとMySQLのスロークエリログ。スコアはほぼ変わらない(3392〜3459)ので、常時入れておいてよい
3. slow.txtとalpの上位を見てから、手を動かす

## 優先順位
1. インデックス: 主キーしかないテーブルは、これだけで約2.5倍(3400→8523)。コストが最も低く、アプリを触らない
2. N+1の解消、重い画像のnginx配信など、アプリの変更
3. 複数台への分割、カーネルやnginxのチューニング

効果の大きい順ではなく、変更が小さくて戻しやすい順に進める。

## 運用ルール
- 1回の変更は1つだけ。`make try`のたびに`results/ledger.tsv`へ記録される
- passがfalse、またはスコアが計測のばらつき以下なら戻す
- 設定はサーバ上で直接編集しない。リポジトリのconf/配下とsql/indexes.tsvに置き、デプロイで反映する
- 複数人で作業するときは、検証をリース経由(`make try`)で直列化する。ベンチを同時に走らせない
- 終わったらインスタンスを削除する(停止だけでは料金が残る)。提出前に計測用の設定を外す

## 複数人での進め方
- 基本は各自が別のworktreeとブランチで作業し、`make try`で順番に検証する(`make wt`でworktreeを作る)
- 詰まったときだけ、Live Shareか画面共有で一時的にペアになる
- ペアの間は、ホスト1人がコミットとpushを担当する。`make try`のラベルとdocs/claims.mdの記載も、その1人分に揃える

## 環境ごとの落とし穴
ISUCON13の練習環境で、そのままでは動かなかった点は[examples/isucon13/README.md](../examples/isucon13/README.md)にある。DNSの応答先、期限切れ証明書、ベンチの出力形式の3つ。
